7 · Entrega final · Pruebas de Qolqe

Esta lámina responde la primera observación: que quede clara la arquitectura del proyecto de automatización, API y web. Se lee de izquierda a derecha. El Gherkin dice qué se prueba. Los pasos lo traducen: pytest-bdd en Python para la API y playwright-bdd en TypeScript para la web. Después, lo que habla con Qolqe: en la API, el cliente Sesiones, hecho con httpx, que guarda el token de cada usuario; en la web, los Page Objects y sus componentes, así que ningún paso tiene un localizador. Y al final cada suite deja su JUnit y su reporte HTML. El contrato no pasa por Gherkin: Schemathesis lee el OpenAPI de Qolqe y genera los casos. El rendimiento tampoco: k6 corre a mano contra Qolqe en un contenedor de 1 CPU, fuera del pipeline, y su evidencia queda versionada en el repositorio. Las partes comparten artefactos, no código: el Gherkin con sus etiquetas, la API de soporte y el formato JUnit. Por eso el JUnit es el punto de unión: de ahí salen la matriz, el historial de Pages y los Test Runs de Kiwi. Si pregunta por qué dos lenguajes: cada capa usa el runner que enseña la clase. La clase 10 enseña pytest con pytest-bdd y Schemathesis, en Python, que además es el lenguaje de Qolqe; la clase 11 enseña Playwright con playwright-bdd, en TypeScript, y su runner trae integradas las repeticiones, los reintentos y las trazas. El costo es real y está escrito: dos gestores de dependencias y los usuarios de prueba repetidos en las dos suites.
