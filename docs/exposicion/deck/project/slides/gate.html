PUNTO 5 · QUALITY GATE

Cuatro criterios de salida, y quién los hace cumplir

Si uno falla, el PR no entra a main: api y web son checks obligatorios, también para el dueño, y quality-gate da el veredicto en el resumen. Probado en el PR #10: run #25 en rojo, fusión bloqueada.

1 · ANÁLISIS ESTÁTICO · estatico

Lint, tipos, Gherkin con todos sus pasos definidos, etiquetas de trazabilidad, el propio workflow y la regla del patrón

2 · CONTRATO · contrato

Los casos generados desde el OpenAPI pasan, y corren antes que las pruebas funcionales

3 · API FUNCIONAL Y TÉCNICA · api

Todas pasan; los defectos conocidos, como fallo esperado estricto con su DEF

4 · WEB · web

Pasa las tres corridas seguidas, sin ninguna prueba inestable

Se lee en el resumen del run, sin abrir el YAML. No evalúa el rendimiento, que se mide aparte con 1 CPU, ni el job de reportes, que publica aunque fallen las pruebas.

13 · Entrega final · Pruebas de Qolqe

El anuncio pide que los quality gates estén claros. Claro significa dos cosas: qué mide y qué pasa si falla. Qué pasa si falla está arriba: el pull request no entra a main. La protección de main exige dos checks obligatorios, api y web, y la regla se aplica a todos, así que tampoco el dueño del repositorio puede fusionar sin los dos en verde. Esos dos bastan para los cuatro criterios: cada job comprueba al anterior, así que si estático o contrato fallan, api y web también quedan en rojo. quality-gate es el que junta los cuatro resultados y escribe el veredicto en el resumen. Lo probé de verdad: el PR #10 rompe a propósito el saldo esperado de un caso; en su run, el #25, api quedó en rojo, web falló en su guarda en vez de omitirse, quality-gate dio «no pasa» y la fusión quedó bloqueada. Qué mide: el job quality-gate escribe en el resumen del run los cuatro criterios de salida y el job que hace cumplir cada uno. Antes había que abrir el YAML para saber qué significaba «pasa». Y dice también lo que no evalúa: el rendimiento, porque se mide aparte en un entorno controlado, y el job de reportes, que corre incluso cuando las pruebas fallan, porque el reporte es justamente lo que explica el fallo. Un gate que no declara su alcance invita a creer que cubre más de lo que cubre. Si pregunta por qué el rendimiento no está en el pipeline: con un solo usuario, el login ya da 92 milisegundos frente a los 80 de margen que exige mi criterio de validez. En un runner compartido de GitHub eso daría rojos falsos y bloquearía merges sin que nada se haya roto.
